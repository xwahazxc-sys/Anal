# Architecture: сканер продуктов (пересборка основных функций Yuka)

## Stack

| layer | choice | why |
| --- | --- | --- |
| mobile | Expo (React Native) + TypeScript, expo-camera для штрихкодов | основной сценарий — камера в магазине; одна кодовая база на iOS и Android |
| web | Next.js на Vercel, только лендинг и страницы продуктов (позже) | не нужно для основного цикла |
| database | Postgres на Supabase | один сервис: база, авторизация, хранилище |
| auth | Supabase Auth (email, Apple, Google) | Apple обязателен, если есть другой вход |
| payments | RevenueCat поверх Apple/Google IAP | покупки внутри приложения обязаны идти через магазины, Stripe для мобильных подписок нельзя |
| email | Resend | письма о подтверждении и сбросе пароля |
| jobs | Supabase Edge Functions + pg_cron | пересчёт оценок, проверка загрузок, чистка |
| files | Supabase Storage | фото упаковок и состава |
| OCR | Google Cloud Vision (свои ключи) | распознавание текста на фото состава |
| hosting | Supabase (бэкенд), EAS Build для сборок | |

Источник данных о продуктах: открытая база (Open Food Facts, лицензия ODbL, нужно указание источника) как старт, затем пользовательские добавления. Это ваши данные, не база Yuka.

## Schema

Tables: 8. Access rules: RLS (см. `replica/schema.sql`).
`products` и `ingredients` читаются всеми, пишутся только сервисной ролью. Остальное доступно только владельцу. `subscriptions` пишет только вебхук.

Webhooks in: RevenueCat. Webhooks out: нет.
Jobs:
- `process_submission` — при создании заявки: OCR, проверка доли нераспознанного текста (более 20% уходит на ручную проверку), создание продукта.
- `recompute_scores` — ночью, если вырос `score_version`.
- `expire_premium` — ежечасно, сверка `premium_until`.
- `purge_deleted_users` — ежедневно, удаление данных по запросу.

## The parts that bite

- Формула оценки: Yuka публикует 60/30/10 и потолок 49 при рискованной добавке, но пороги питательности (аналог Nutri-Score) надо взять из открытого описания Nutri-Score. Оценку косметики строим по собственному справочнику рисков. Записывать `score_version`.
- Справочник ингредиентов: самое трудоёмкое. Оценки писать своими словами по открытым научным источникам, не копировать тексты Yuka.
- Покупки: правила Apple и Google, возвраты, восстановление покупки, grace-период; статус считать по вебхуку, а не по клиенту.
- Идемпотентность: вебхуки приходят повторно; `unique (provider, provider_ref)` и обновление по событию.
- Гонки: два пользователя добавляют один штрихкод; `products.barcode` уникален, заявка сливается с существующим.
- Офлайн: пакет данных (популярные продукты) с версией, разрешение конфликтов не нужно, история пишется локально и отправляется позже.
- Время: `timestamptz` в UTC; история показывается в поясе устройства.
- Разрешения: камера, отказ пользователя, ручной ввод штрихкода как запасной путь.
- Лицензии данных: ODbL (указать источник, делиться изменениями базы), фото продуктов могут иметь свои лицензии.
- Удаление по GDPR: заявки остаются без привязки к пользователю (`on delete set null`), остальное удаляется каскадом.
- Здоровье: оценка не медицинская рекомендация, нужна оговорка в приложении и условиях.

## Build order

1. Vertical slice (S01, S02, S04; таблицы `profiles`, `products`, `ingredients`, `product_ingredients`, `scan_events`; маршруты by-barcode и history): регистрация, скан, карточка с оценкой из загруженной открытой базы, запись в историю.
2. Must-haves: S03 альтернативы, S06 добавление продукта (`submissions`, `process_submission`), цветовая шкала и потолок 49, косметика, подписка (S09, `subscriptions`, вебхук).
3. Should-haves: избранное S05, поиск S07, предпочтения S08, офлайн, фонарик, проверка данных вручную.
4. Fixes from replica-entrepreneur: после его запуска.
